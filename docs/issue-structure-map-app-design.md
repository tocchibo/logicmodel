# 課題構造マップ自動生成・編集アプリ 設計方針

## 目的

このドキュメントは、現行のロジックモデル描画アプリを参考に、AIが生成した「課題構造マップ」を貼り付けて可視化・微修正できる静的Webアプリを作るための設計方針を整理する。

前提として、AIとの連携はAPI連携ではなく、汎用チャットAIにシステムプロンプトを与え、生成結果をユーザーがコピーしてアプリへ貼り付ける方式とする。これは現行アプリのコマンド貼り付け方式と同じ運用である。

## 課題構造マップの扱い

課題構造マップは、特定テーマの社会課題について、個別の課題状態、構造要因、前提条件、課題同士の因果関係、根拠を整理するためのマップとして扱う。

ロジックモデルとの違いは、ロジックモデルが「介入によって何が変わるか」を順方向に設計するのに対し、課題構造マップは「なぜその問題が維持・拡大しているか」を現状構造として分析する点にある。そのため、ノードには施策ではなく課題状態や構造要因を置く。

## 基本方針

- AI出力とアプリ内部状態はJSONを正とする。
- Markdown、Mermaid、Graphviz DOTは、AIの主出力形式にはしない。
- 描画時だけJSONからGraphviz DOT、Cytoscape.js形式、または独自SVG描画用データへ変換する。
- 初期MVPでは既存アプリのViz.js/Graphviz方式を活かす。
- 編集体験の限界が見えたら、描画層をCytoscape.jsまたはELK.js + 独自SVGへ差し替える。
- GitHub Pagesで動く静的サイトとして維持し、バックエンドや秘密情報を必要としない。

## 推奨データ形式

AIには、次のようなJSONを生成させる。

```json
{
  "schemaVersion": "issue-map/v1",
  "title": "地方小規模都市の課題構造マップ",
  "scope": {
    "theme": "地域活性化",
    "geography": "日本の地方小規模都市",
    "targetPopulation": "地域住民・事業者・自治体",
    "assumptions": [
      "人口減少と高齢化は短期には前提条件として扱う"
    ]
  },
  "perspectives": [
    { "id": "work", "label": "仕事", "color": "#2f9e6d" },
    { "id": "life", "label": "暮らし", "color": "#4aa3a1" },
    { "id": "values", "label": "価値観", "color": "#9bbf6b" }
  ],
  "nodes": [
    {
      "id": "n001",
      "label": "賃金水準が低い",
      "type": "issue",
      "perspective": "work",
      "layer": "structure",
      "status": "hypothesis",
      "evidenceIds": ["ev001"]
    }
  ],
  "edges": [
    {
      "id": "e001",
      "from": "n001",
      "to": "n002",
      "relation": "causes",
      "polarity": "+",
      "confidence": "medium",
      "rationale": "賃金水準の低さが就業先としての魅力を下げる"
    }
  ],
  "evidence": [
    {
      "id": "ev001",
      "title": "出典名",
      "url": "",
      "note": "根拠メモ"
    }
  ],
  "layout": {
    "engine": "auto",
    "positions": {},
    "pinnedNodeIds": []
  }
}
```

## データ項目の考え方

### scope

マップの対象範囲を明示する。AI生成ではテーマが広がりすぎやすいため、地域、対象者、前提条件をJSON内に残す。

### perspectives

SIIF事例で見られるような観点レイヤーを表す。例として、地域活性化なら「仕事」「暮らし」「価値観」「自然環境」、ヘルスケアなら「ヘルスシステム」「ヘルスリテラシー」「ソーシャルキャピタル」のように使う。

### nodes

ノードは課題状態、構造要因、前提条件、外部環境などを表す。施策や活動は原則としてノードに混ぜない。

推奨する `type` は次の通り。

- `issue`: 解決対象となる課題状態
- `structural_factor`: 課題を生む構造要因
- `assumption`: 短期には変えにくい前提条件
- `external_factor`: 外部環境
- `mental_model`: 価値観、固定観念、文化的前提

推奨する `layer` は次の通り。

- `event`: 表層の事象
- `pattern`: 繰り返される傾向
- `structure`: 制度、資源配分、関係性、情報流通などの構造
- `mental_model`: 背後の価値観や認識

### edges

エッジは必ず `from` が原因、`to` が結果になるようにする。

`polarity` は、原因側が増えたときに結果側がどう変わるかを表す。

- `+`: 同方向に増幅する
- `-`: 逆方向に作用する
- `unknown`: 判断できない

`confidence` は、AIの仮説と根拠の強さを分けて扱うために使う。

- `high`
- `medium`
- `low`

### evidence

根拠や参考情報を保持する。AIが確実な出典を持たない場合は、空欄や仮説メモとして残す。根拠が弱い課題は `status: "hypothesis"` として扱う。

### layout

初期段階では自動レイアウトでよいが、ユーザーがノード位置を微修正できるようにする場合は `positions` と `pinnedNodeIds` を保持する。

## AIへの指示方針

汎用チャットAIには、システムプロンプトで次を強く指定する。

- 出力はJSONのみとする。
- `schemaVersion` は `issue-map/v1` とする。
- ノード数は初期版で25から45程度、詳細版で40から70程度にする。
- ノードは短い課題状態として書く。
- 施策、解決策、ToDoを課題ノードに混ぜない。
- エッジは必ず原因から結果へ向ける。
- 因果関係が不確かなものは `confidence: "low"` にする。
- 根拠が弱いものは `status: "hypothesis"` にする。
- 修正依頼への応答も差分ではなく完全なJSONを返す。

## 可視化ライブラリの選択

### Viz.js / Graphviz

現行アプリで使っている方式。JSONからGraphviz DOTを生成し、Viz.jsでSVG化する。

メリット:

- 既存の構成を流用しやすい。
- 自動レイアウトが強い。
- SVG/PNGエクスポートとの相性がよい。
- 静的サイトで動かしやすい。

デメリット:

- ノードの手動配置やドラッグ編集はやや難しい。
- 背景レイヤーの細かい表現には工夫が必要。
- 複雑な循環的因果関係では、期待通りの配置にならない場合がある。

MVPでは第一候補とする。

### Cytoscape.js

インタラクティブなネットワーク図を作るためのライブラリ。ノード、エッジ、パン、ズーム、ドラッグ、選択、スタイル制御が揃っている。

メリット:

- 編集UIとの相性がよい。
- ノードのドラッグ、選択、ハイライトが実装しやすい。
- 複雑なネットワーク構造を扱いやすい。

デメリット:

- SIIF風の整理された紙面レイアウトを作るには調整が必要。
- SVG/PNG出力やラベル整形は個別対応が必要になる。

編集体験を重視する第2段階の候補とする。

### ELK.js + 独自SVG

ELK.jsでレイアウト計算を行い、描画は自前のSVGで行う方式。

メリット:

- レイヤー、帯、グループ、エッジ形状を細かく制御しやすい。
- SIIF風の整理された構造図に近づけやすい。
- レイアウト結果と手動配置を組み合わせやすい。

デメリット:

- 描画、選択、編集、エクスポートをかなり自作する必要がある。
- MVPには重い。

本格版の候補とする。

### D3

描画やズーム、ドラッグの補助としては有用。ただし、課題構造マップの自動レイアウトをD3だけで作ると実装量が大きくなる。

単独の主描画エンジンではなく、補助的に使う候補とする。

### Mermaid

AI出力との相性はよいが、課題構造マップの内部データとしては情報量が不足しやすい。根拠、観点、粒度、仮説状態などを保持しにくい。

プロトタイプや説明用には使えるが、アプリの中核にはしない。

## MVP実装方針

MVPでは、既存アプリの構造を活かして次を作る。

1. JSON貼り付け欄を用意する。
2. `issue-map/v1` の最低限のバリデーションを行う。
3. `IssueMapData` を `AppState.issueMapData` のような中央状態として保持する。
4. JSONからGraphviz DOTを生成する。
5. Viz.jsでSVG表示する。
6. SVG上のノード、エッジをクリックして編集パネルを開く。
7. ノードのラベル、種類、観点、レイヤー、根拠IDを編集できるようにする。
8. エッジの向き、極性、信頼度、理由を編集できるようにする。
9. ノードを選ぶと、周辺エッジを自動的にハイライトする。
10. 修正後のJSONを保存できるようにする。
11. AIへの再修正指示をコピーできるようにする。

## 既存アプリから流用できるもの

- 静的HTML/CSS/JavaScript構成
- CDNでViz.jsを読み込む構成
- `AppState` による中央状態管理
- JSON保存・読み込み
- SVG/PNGダウンロード
- SVG要素へのクリックイベント付与
- 編集パネルの考え方
- Undo/Redoの考え方
- AIへの修正指示をコピーする運用

## 新規に必要なもの

- `IssueMapData` スキーマ
- JSONバリデーション
- AI出力の正規化処理
- 課題ノード用の編集UI
- エッジ属性用の編集UI
- 根拠情報の表示・編集UI
- 観点別の色分け
- レイヤー別の視覚表現
- JSONからDOTへの変換ロジック
- AI向けシステムプロンプトと修正プロンプト生成

## 段階的な開発案

### Phase 1: JSON貼り付けと表示

- JSON貼り付け欄を作る。
- JSONを検証する。
- Graphviz DOTへ変換する。
- SVGとして表示する。

### Phase 2: 基本編集

- ノードのラベル、種類、観点を編集する。
- エッジの向き、極性、信頼度を編集する。
- JSON保存・読み込みを実装する。

### Phase 3: 課題構造マップらしい機能

- ノード選択時の周辺エッジハイライトを実装する。
- 根拠情報を表示・編集する。
- 前提条件と解決対象を切り替えて表示する。
- 観点別、レイヤー別の表示フィルターを実装する。

### Phase 4: AI修正運用

- 編集済みJSONと追加指示を組み合わせた修正プロンプトを生成する。
- AIが返した完全JSONを貼り付けて再描画できるようにする。
- 粒度が粗すぎる、施策が混ざっている、因果向きが曖昧、といった警告を出す。

### Phase 5: 描画層の改善

- Viz.jsで十分なら継続する。
- 手動配置や編集体験が重要になったらCytoscape.jsへ移行する。
- SIIF風の整理された紙面表現を重視するならELK.js + 独自SVGを検討する。

## 注意点

- AI出力は仮説として扱う。根拠が弱いものを確定情報として表示しない。
- 課題ノードに解決策を混ぜると、構造分析と施策設計が混線する。
- JSONスキーマは最初から複雑にしすぎない。
- 可視化の美しさより、因果向き、粒度、根拠、選択時の関係把握しやすさを優先する。
- 静的サイトとして動く制約を守り、APIキーやサーバーを必要とする設計にしない。

## 当面の結論

最初の実装は、`IssueMapData` JSONをAIに生成させ、アプリに貼り付け、Viz.jsでSVG表示する方式がよい。現行アプリの設計資産を最大限流用でき、GitHub Pagesでの公開制約にも合う。

ただし、課題構造マップはロジックモデルよりも関係線の可読性と手動調整の重要度が高い。そのため、MVPの後に編集体験を検証し、必要に応じてCytoscape.jsまたはELK.js + 独自SVGへ描画層を移行する余地を残しておく。
